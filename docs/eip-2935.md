# L2 block-hash history (EIP-2935)

The fresh-chain genesis generator installs the canonical [EIP-2935 history
account](https://eips.ethereum.org/EIPS/eip-2935) because the supplied genesis
template enables Feynman at timestamp zero. This is L2 execution history;
`L1BlockContainer` serves a different purpose.

## Genesis account

- Address: `0x0000F90827F1C53a10cb7A02335B175320002935`.
- Nonce: `1`; balance: `0`; storage: empty (no backfill, including no genesis hash).
- Runtime: the EIP's 83-byte runtime, excluding the 9-byte deployment constructor.
- Runtime keccak256: `0x6e49e66782037c0555897870e29fa5e552daf4719552131a0abce779daec0a5d`.
- Direct code installation, without a proxy, owner, initializer, or configurable address.

`BlockHashHistory.sol` pins the runtime; `GenerateGenesis.setBlockHashHistory()`
installs it. At block 1 the execution client writes the genesis hash to slot 0.
At block N it writes the L2 parent hash to `(N - 1) % 8191` before transactions.
A read uses a raw 32-byte big-endian block number, without an ABI selector. Reads
within `[max(0, N - 8191), N - 1]` return a 32-byte hash; malformed input and
out-of-window reads revert. An in-window entry not yet populated returns zero.

The client system call must use caller
`0xfffffffffffffffffffffffffffffffffffffffe`, 32-byte L2 parent hash, zero value,
and 30,000,000 gas. It must complete outside user transactions, without consuming
block gas, transferring fees, or warming the account/storage for the first user
transaction. An absent account silently does nothing. Merely installing code on
a client without the system call will leave history empty.

Both inspected client families already obtain post-Feynman `BLOCKHASH` results
from history storage while retaining the 256-block window. This PR changes no
opcode implementation. Preserving results at a later activation boundary,
particularly for pre-activation blocks, needs explicit client validation: an empty
ring buffer cannot supply those older hashes. EIP-2935 itself does not change
`BLOCKHASH` semantics.

## Existing networks

Generating a new genesis does not modify an initialized chain. Do not replace an
existing chain's genesis or rerun genesis generation as a network upgrade.

Before selecting an activation block, query `eth_getCode`,
`eth_getTransactionCount`, and `eth_getStorageAt` on each deployed client and
record its binary/image revision and fork schedule. This repository does not
establish whether a deployed network already installed the account by another
path. If it already has the canonical account and populated history, preserve
that account and storage.

For an existing chain without the account, coordinate a client release with an
explicit future installation boundary. All participating clients must install the
canonical code and nonce before the first system call at that boundary; preserve
any existing balance and reject conflicting code instead of overwriting it.
The first write at activation block A is hash(A-1), with no backfill. Do not reset
history on subsequent blocks or replay. If choosing the EIP's canonical deployment
transaction instead, verify the chain accepts its signature, fees, and constructor;
installation within block A means the first pre-block write can only occur in A+1.
Ordinary deployment cannot write history using the reserved system caller.

A future client release must specify this installation boundary and any required
`BLOCKHASH` compatibility handling. This contracts PR does not assign an existing
network's activation height, ship that client transition, or claim cross-client
replay equivalence. Those remain release gates tracked by issue #73.

## Verification

`bash docker/scripts/verify.sh` includes this account in the deployment
verification flow. It compares chain runtime bytes and nonce against the protocol
constants at one block hash and fails on a missing/mismatching account or RPC
error. It does not submit the `BlockHashHistory` constants library to an explorer
as the history contract's Solidity source. This check uses `cast` and the same
`contracts.verification.RPC_URI_L2` setting as the other L2 contracts; no address
configuration or override is needed.

Run the runtime and genesis serialization tests:

```sh
forge test --evm-version cancun --match-path 'src/test/{BlockHashHistory,GenerateGenesis}.t.sol'
```

They verify exact runtime/nonce/empty storage, successful reads, invalid lengths,
current/future/expired queries, the inclusive 8191-block boundary, full rollover,
ordinary callers being unable to write, and a partially filled buffer after a
modeled activation. The Forge system caller is a simulation, not proof of client
block processing.

CI additionally exercises the actual `GenerateGenesis.run()` entry point and
checks its output alloc, independently of the test harness that installs the
history account directly. Run this check without a client checkout:

```sh
python3 scripts/integration/test-eip2935.py --genesis-only
python3 -m unittest discover -s scripts/integration -p 'test_block_hash_history.py' -v
```

Removing the installation call from `generateGenesisAlloc()` must fail the first
check. Both commands run in the Foundry CI job.

Run the generated-genesis integration test with a clean DogeOS geth checkout at
`33c46866196da34484bf1bfbaab20aa4929b3fcc`:

```sh
python3 scripts/integration/test-eip2935.py --geth-repo /path/to/go-ethereum
```

This creates a temporary configuration with a public test key, runs the actual
contract-address and genesis generators, and passes the resulting alloc to geth's
`StateProcessor`. In blocks 1 and 2, a signed contract-creation transaction reads
history and executes `BLOCKHASH` for the parent. The test checks both values
against the actual parent header hash, the ring-buffer storage, and that block
gas equals transaction receipt gas. It never sends transactions to a running
network and leaves the user's `volume/` untouched. Dependencies: forge, jq, Go,
and this repository's installed Solidity/Node dependencies.

The test adapts only the JSON encoding of `l1ChainId` and
`numL1MessagesPerBlock` to legacy geth's quoted-number requirement; the generated
alloc is unchanged. A fake sealing engine is used, so this verifies geth execution
of the history account, not geth compatibility with the complete Tsuki chain.
Cross-client replay, Reth execution, and an existing-network installation
transition still need their client release tests.

After booting a disposable client with the generated genesis and producing at
least two blocks, use the read-only Python 3 smoke check:

```sh
python3 scripts/check-block-hash-history.py --block 1 http://127.0.0.1:8545
python3 scripts/check-block-hash-history.py --block 2 http://127.0.0.1:8545
# At a later installation boundary, use the first block that actually writes:
python3 scripts/check-block-hash-history.py --activation-block 100 --block 100 http://127.0.0.1:8545
# Compare clients following the exact same chain at a fixed height:
python3 scripts/check-block-hash-history.py --block 8192 http://127.0.0.1:8545 http://127.0.0.1:9545
```

The script checks canonical runtime and nonce, parent/oldest-retained hashes,
unfilled pre-activation history where applicable, matching storage and call
results, and matching block hashes/state roots across supplied endpoints. It
requires historical state for the chosen height and EIP-1898 support for
`eth_getCode`, `eth_getTransactionCount`, `eth_call`, and `eth_getStorageAt`.
All state reads use the selected block hash with `requireCanonical: true`; the
expected parent comes directly from that block's header. The script rechecks the
canonical header before returning, failing if it changed while older expected
hashes were read. An unavailable/orphaned snapshot or an RPC that does not support
EIP-1898 fails the check; there is no fallback to mutable height-based state reads.
Retry after a reorg using an available canonical block.
It sends no transactions and uses no state overrides. A mismatching state root
fails even when the sampled history slots match.

Client integration qualification must additionally execute a user transaction
that reads the parent hash in the activation block, verify receipt/block gas and
cold-access behavior, replay the same blocks on each supported client, and test
activation/reorg boundaries plus the 256-block `BLOCKHASH` window. Comparing RPC
state alone cannot prove transaction ordering or replace replay tests.
